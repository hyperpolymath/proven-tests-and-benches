= Component Readiness Grade (CRG)
:toc: left

Follows the estate Component Readiness Grade convention (CRG v1.0,
`hyperpolymath/standards`), as used by sibling repos `panic-attack`
(`READINESS.md` + `tests/readiness.rs`) and `proven-servers`.

== Grade scale

WARNING: *This ladder is not the estate standard, and the grade below is
measured against it rather than against CRG.* Flagged 2026-08-03; reconciling
it is an owner decision and has deliberately not been done unilaterally.

The estate standard is *Component Readiness Grades v2.2*
(`hyperpolymath/standards/component-readiness-grades/COMPONENT-READINESS-GRADES.md`),
whose scale is `X F E D C B A` — seven rungs, not four — and whose rung
definitions differ materially from the four below:

[cols="1,3,4"]
|===
| Grade | CRG v2.2 name | What CRG v2.2 actually requires

| D | Partial / Inconsistent (alpha-unstable)
| A matrix of tested scenarios; documented scope; at least one test per claimed
  capability; *RSR compliance*; *Immaculate Guide compliance* — including
  `.tool-versions` pinning all tools and `panic-attack assail` passing.

| C | Self-Validated (alpha-stable)
| Dogfooding on the project itself; *CI integration or equivalent automated
  validation in the home context*; no known failures in the home context; deep
  annotation. Per the Testing Taxonomy's CRG mapping, C additionally requires
  unit + P2P + E2E + smoke + reflexive + build + contract + aspect tests all
  passing, and *benchmarks baselined*.

| B | Broadly Validated (beta-stable)
| Tested on *at least six genuinely diverse external targets*, with results and
  evidence that findings were fed back. Not "handles edge cases".

| A | Field-Proven (stable)
| Real-world external usage data and evidence of feedback incorporation.
|===

Two CRG C requirements are currently *not* met, which is why the grade below
should not simply be carried across:

* *No automated validation on push or PR.* `.github/workflows/ci.yml` is
  `workflow_dispatch:`-only and no GitLab remote is configured in this
  checkout, so the Idris2 gate runs only when a human triggers it.
* *Benchmarks are not baselined.* There is a working harness but no baseline,
  no thresholds, no history and no regression gate. See `TEST-NEEDS.md` Gap C.

The four-rung ladder retained below is what the grade in _Current status_ was
actually assessed against, and is kept verbatim so the assessment remains
interpretable rather than being silently re-scored.

[cols="1,2,5"]
|===
| Grade | Name | Machine-verifiable meaning (LOCAL ladder, not CRG v2.2)

| D | Alpha | Component runs without crashing on valid input
| C | Beta | Component produces correct output on representative input
| B | RC | Component handles edge cases and multiple input types
| A | Stable | Sustained correct operation under adverse conditions
|===

== Current status

Current Grade: C

*Evidence for D (Alpha):* the framework library (23 modules) compiles under
Idris2, installs, and its self-test suite runs green via `scripts/ci-build.sh`
(the CI gate). The type-safe suite package (`proven-tests-suite.ipkg`) builds
against the installed library and passes. Machine-checked content includes
`src/ProvenTests/Tropical.idr` (total semiring proofs) and
`src/ProvenTests/Meta.idr` (coverage-derivation lemmas), plus the
evidence-carrying provenance types.

*Evidence for C (Beta):* the framework now produces correct, useful output
about a *real external subject*. `integrations/proven/` grades all 88 of
proven's modules by three-tier provenance, parsing proven's own
`MODULE-STATUS.txt` and OWED ledger. Its as-declared reading (4 Actually / 37
Provisionally / 47 Unproven) reconciles exactly with proven's own header
(4 FIRST + 37 SECOND + 47 WIP), and its strict evidence-carrying reading
surfaces the drift: 0 modules are Actually-Proven, because proven's four
proof-bearing modules all still sit in its 256-axiom OWED ledger. Meta-tests
demonstrate the framework detects a deliberately failing test.

== Criteria to advance

*To C (Beta):* the framework must produce correct, useful output about a real
external subject — the provenance-graded module report for `proven`
(`integrations/proven/`) running against a live checkout and reconciling with
that repo's own module ledger.

*To B (RC):* subject tests exercising a real dependency (`depends = proven`)
pass; the machine-readable run report (`--report`) is emitted and consumed by
at least one downstream tool (panic-attack `aggregate`); meta-tests
demonstrate failure detection (a deliberately failing test fails the suite).

*To A (Stable):* FFI-parity golden-vector harness operational against at least
one proven binding (blocked on `proven` producing a real Idris-backed
`libproven`); mutation/meta-testing demonstrates the suite kills seeded
defects.
